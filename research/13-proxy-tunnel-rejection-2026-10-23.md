# 13 — Прокси: 407-стена авторизации — это «недоступен», а не «не определён»

Дата: 2026-10-23. Метод: живая диагностика пула (29 выходов, keyless
`GET /v1/models` через каждый — без ключа и без квоты), локальный HTTP-прокси,
отвечающий 407 на CONNECT, для снятия формы ошибки undici 8.10.2.

## §1. Вопрос пользователя и что он вскрыл

Вопрос к сводке `proxy check` («ok: 21, недоступны: 0, не определены: 8 — они
работают или нет?») показал: сводка даёт три голых числа, а «не определены: 8»
не говорит ни о чём. Диагностика пула уточнила причину — и обнаружила дефект
классификатора.

Живой замер (2026-10-23, keyless `GET /v1/models`, 29 выходов): 21 выход
ответил HTTP 200, и **все 8 «неопределённых» отвечали одинаково**:

```
AbortError[UND_ERR_ABORTED] Proxy response (407) !== 200 when HTTP Tunneling
```

Это прокси, требующие авторизацию: CONNECT не建立, до NIM запрос не доходит.
Выход **точно не работает** — но ундичи отдаёт это как `UND_ERR_ABORTED`,
которого нет в списке CONNECT-класса (`proxy-pool.ts`), поэтому проба
классифицировала его как `unknown`. Цифра маскировала определённый отказ.

## §2. Форма ошибки undici

Локальный прокси, отвечающий 407 на CONNECT, дал ту же форму, что и боевые
выходы (проверено на undici 8.10.2 из поставки pi 1.4.0):

```
name: AbortError | code: UND_ERR_ABORTED
msg:  Proxy response (407) !== 200 when HTTP Tunneling
statusCode: undefined | own props: [ 'stack', 'message', 'name', 'code' ]
cause: undefined
```

Ни `statusCode`, ни `cause` в ошибке нет — распознать отказ CONNECT можно
только по тексту сообщения. Источник: `undici/lib/dispatcher/proxy-agent.js`
(`if (statusCode !== 200) { … callback(new RequestAbortedError(\`Proxy response
(${statusCode}) !== 200 when HTTP Tunneling\`)) }`).

## §3. Правки

1. **Классификатор** (`extensions/proxy-pool.ts`): в `isConnectClassError`
   добавлено распознавание отказа туннеля по тексту
   (`/Proxy response \(\d{3}\) !== 200 when HTTP Tunneling/`). Любой не-200 на
   CONNECT — это отказ CONNECT: 407 — стена авторизации, 502/503 — прокси не
   смог связаться с origin. Такой выход классифицируется как `unreachable`:
   живой dispatch карантинит его так же, как ECONNREFUSED, а `proxy
   cleanup-dead` (unreachable дважды подряд) вычищает из файла пула.

   Проверено на живом пуле: до правки 21 ok / 0 unreachable / 8 unknown, после
   — 21 ok / 8 unreachable / 0 unknown.

2. **Сводка `proxy check`**: каждый не-ok выход перечисляется с причиной —
   стена авторизации прокси / отказ соединения (с кодом) / таймаут пробы
   («выход может быть медленным, не обязательно мёртвым») / прочее. Раньше
   сводка давала только три числа, из которых «не определены: 8» ни о чём не
   говорило, хотя причины у этих восьми были однородны и лечились одинаково.

3. **Белые списки глаголов** у `keys` и `proxy` теперь деривируются из
   каталога команд (`commands.ts`), а не дублируются вручную: тот же класс
   рассинхрона уже ломал `keys auth-check` («неизвестный аргумент» при
   аргументе, который сама команда и предлагала).
