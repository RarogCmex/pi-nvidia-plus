# 09 — Валидация ключа NIM без генерации: оракул 403/404

**Дата:** 2026-10-10 (вечер) · **Метод:** `POST /v1/chat/completions` с ключом
и телом, из которого выброшено поле `messages` — модель берётся из живого
keyless-каталога. Контрольные пробы фейковым ключом (`nvapi-0invalid…`).
Рабочий прогон: 436 ключей пула `nvidia-keys.json`, 3 параллельных потока,
208 с. **Ноль потраченных токенов:** ни один запрос не дошёл до генерации.

**Вопрос:** штатный `/nvidia-plus keys check` шлёт настоящий мини-чат
(`max_tokens: 8`) — то есть тратит квоту на каждый ключ, и пул из сотен ключей
прогревается только ценой сотни генераций. Можно ли узнать, жив ли ключ, не
генерируя ничего? (Постановка владельца: «достаточно, что он не даёт 403».)

## Оракул

Порядок обработки запроса NIM: **авторизация → резолв chat-функции под
аккаунт → валидация тела → генерация**. Третий шаг не нужен: достаточно дойти
до второго. На модели из живого каталога:

| Ключ | Ответ | Смысл |
|---|---|---|
| мёртвый | `403 {"title":"Forbidden","detail":"Authorization failed"}` | кредиты отвергнуты |
| живой | `404 {"title":"Not Found","detail":"Function '…': Not found for account '…'"}` | auth ПРОЙДЕН (аккаунт назван в ответе), функции под аккаунтом нет |
| живой (аккаунт с доступом) | `400/422` — тело невалидно, до генерации не дошло | auth пройден, валидация тела |
| любой, рейт-лимит | `429` | жив, но ограничен |

Эмпирическая проверка (обе стороны оракула, дважды):
фейковый ключ → 403 на любой модели; живой ключ → 404-for-account на
`01-ai/yi-large` и на `deepseek-ai/deepseek-coder-6.7b-instruct` (модель из
каталога, но chat-функция аккаунту недоступна — и это НЕ мешает оракулу).

**Классификация:** dead = 401/403; alive = 200/202/400/404/422/429;
unknown = 5xx/сетевые срывы — не удаляются. Каждый dead подтверждается второй
пробой (ключи — это деньги; ложное удаление дороже повтора).

## Результат рабочего прогона (2026-10-10)

436 ключей: **384 живых** (все — 404-for-account), **52 мёртвых** (все — 403,
каждый подтверждён дважды), 0 неопределённых. Статус-распределение вырождено
в {403, 404} — ни одного 200/400/429, то есть ни один аккаунт пула не имеет
доступа к пробной chat-функции, и это не влияет на валидность. Мёртвые
составили 12% — под порогом защиты от массовой вычистки (50%).

## Методологические оговорки

- **404 двусмыслен вне контекста.** По исследованию 06 NIM резолвит
  НЕСУЩЕСТВУЮЩУЮ модель до авторизации (keyless → 404). Поэтому модель для
  пробы обязана браться из живого каталога: у несуществующей id оракул
  вырождается — все ключи выглядят живыми. Это безопасное направление отказа
  (ложных удалений нет), но и ценность пробы падает до нуля; свежесть каталога
  проверяется keyless `GET /v1/models` перед прогоном.
- **404-for-account не доказывает юзабельность аккаунта** — только что кредиты
  принимаются. Может ли аккаунт вообще запускать модели — отдельный вопрос
  (наш прогон показывает: у всех 384 живых к пробной функции доступа нет).
- **Тело ответа не для логов:** в 404 NIM называет id аккаунта. Скрипт ключей
  печатает и пишет в отчёт только статусы и маски `…XXXX`.
- **Классификатор расширения нельзя переиспользовать напрямую:**
  `classifyKeyProbeStatus` (`extensions/key-check.ts`) считает 404 `unknown` —
  он написан под мини-чат, где 404 значит «модель не та». Под этот оракул
  нужна отдельная таблица статусов (потенциальное улучшение `/nvidia-plus
  keys check`: перестать тратить генерацию на прогрев).
