# 07 — Живая проба kimi-k3: инертная карта мышления, валидные варианты `reasoning_effort` и коллапс, не зависящий от уровня

Дата проб: **2026-10-05** (системные часы машины проб). Метод: живые запросы
`POST /v1/chat/completions` к `integrate.api.nvidia.com` **с настоящим ключом**
(ключ pi из `~/.pi/agent/auth.json`, провайдер `nvidia`), `stream: true`,
`max_tokens: 4000`, один и тот же короткий промпт `Reply with exactly one word:
OK`. Классификация вывода — детектором из [06](06-gateway-recon-keyless-oracles.md)
§4 (`extensions/degenerate.ts`). Значение ключа нигде не печатается и не пишется.

Файл закрывает гипотезу, оставленную в [06](06-gateway-recon-keyless-oracles.md)
§3: «принимают ли NIM-напрямую `"off"` для kimi и деградирует ли он так же —
не проверено, нужен ключ». Ключ появился; проба сделана.

Легенда достоверности, как в остальных файлах `research/`:

- **измерено** — прямой ответ `integrate.api.nvidia.com` в этой сессии;
- **чтение исходников** — по скомпилированному `dist/` pi-ai (символы, не строки);
- **гипотеза** — экстраполяция, требующая проверки.

---

## 1. Карта мышления kimi-k3 была инертной (главная находка)

Встроенный каталог pi-ai (`dist/providers/data/nvidia.json`, запись
`chat:moonshotai/kimi-k3`) несёт:

```
reasoning: true
compat.supportsReasoningEffort: false
compat.thinkingFormat: undefined
thinkingLevelMap: undefined
```

Наш оверрайд (`overrides/models.json`) добавлял `reasoning: true` и
`thinkingLevelMap: { off: "off", minimal/low: "low", medium…max: "on" }` — но
**не трогал `compat`**.

**Чтение исходников** pi-ai `dist/api/openai-completions.js`, функция построения
параметров: все ветки, потребляющие `thinkingLevelMap`, требуют либо конкретного
`compat.thinkingFormat` (`zai`/`qwen`/`deepseek`/`baseten`/`together`/…), либо
`compat.supportsReasoningEffort`. Две последние ветки:

```js
else if (options?.reasoningEffort && model.reasoning && compat.supportsReasoningEffort) {
    params.reasoning_effort = model.thinkingLevelMap?.[options.reasoningEffort] ?? options.reasoningEffort;
}
else if (!options?.reasoningEffort && model.reasoning && compat.supportsReasoningEffort) {
    const offValue = model.thinkingLevelMap?.off;
    if (typeof offValue === "string") params.reasoning_effort = offValue;
}
```

У kimi `thinkingFormat` отсутствует, а `supportsReasoningEffort` был `false`,
поэтому **ни одна ветка не срабатывала**: `thinkingLevelMap` никогда не
потреблялся, и pi не добавлял в запрос ни `reasoning_effort`, ни thinking-поле.
`extensions/transform.ts` kimi тоже не обрабатывает (нет семейства). Итог: на
любом выбранном уровне пи шёл **голый запрос** — поведение «по умолчанию».

Следствие измерено: голый запрос (конфиг `absent`) на тривиальный промпт
рассуждал неограниченно и в первой приёмочной пробе **не уложился в 150 с**
(таймаут). То есть селектор мышления для kimi-k3 был декоративным, а модель по
умолчанию висла.

Контраст: `z-ai/glm-5.3` имеет ту же инертную карту (`off: "off"`), но **не
виснет**, потому что его обрабатывает хук `transform.ts` (`applyGlmThinking`,
инжект `chat_template_kwargs.enable_thinking` по `ctx.thinkingLevel`). kimi
такого хендлера не имел. `openai/gpt-oss-20b` использует нативный путь
(`supportsReasoningEffort: true`, `off: null`) — и `null` для него безопасен,
потому что gpt-oss без `reasoning_effort` не рассуждает неограниченно.

## 2. Валидные варианты `reasoning_effort` у NIM (измерено)

Проба `reasoning_effort: "off"` дала **HTTP 400** с исчерпывающим перечнем:

```
Failed to deserialize the JSON body into the target type:
unknown variant `off`, expected one of
`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`
```

Значит:

- токена `"off"` у NIM **нет** — старый оверрайд `off: "off"` дал бы 400, если
  бы pi его вообще слал (он не слал — §1);
- значения `"on"` (старые `medium…max: "on"`) тоже **невалидны**;
- валидное множество `none / minimal / low / medium / high / xhigh / max`
  совпадает с уровнями pi **один в один**, кроме pi-уровня `off`, которому
  соответствует NIM-вариант `none`.

Это прямое свидетельство для маппинга: `off → "none"`, остальные уровни —
идентично. `mergeCompat` в pi (`dist/core/provider-composer.js`) делает
`{ ...base, ...override }`, поэтому `compat: { supportsReasoningEffort: true }`
в оверрайде **не затирает** прочие поля встроенного compat (`maxTokensField`
и др.) — только переводит флаг в `true`.

## 3. Поведенческие пробы: латентность и коллапс (измерено)

Две серии. Приёмочная — по одному прогону на конфиг, таймаут 150 с. Фокусная —
несколько прогонов, таймаут 260 с, пауза 3 с между запросами.

Приёмочная (1 прогон, таймаут 150 с):

| конфиг | исход | латентность |
|---|---|---|
| `absent` (голый, как pi сегодня) | **таймаут** | >150 с |
| `reasoning_effort:"off"` | **HTTP 400** (невалидный вариант) | — |
| `"none"` | 200, чистый `OK`, reasoning=0 | 121 с |
| `"low"` | 200, чистый `OK`, reasoning=145 | 127 с |
| `"high"` | 200, чистый `OK`, reasoning=128 | 136 с |

Фокусная (таймаут 260 с):

| конфиг | прогонов | ok | collapse | таймаут | латентность ok/collapse |
|---|---|---|---|---|---|
| `"none"` | 4 | 1 | **2** | 1 | 181–245 с |
| `"low"` | 3 | 1 | **1** | 1 | 163–234 с |
| `absent` | 2 | 1 | **1** | 0 | 136–170 с |

Всего в фокусной серии: 9 прогонов, 3 чистых, **4 коллапса**, 2 таймаута. Даже
короткий ответ приходит за **130–245 с** — kimi-k3 на NIM медленный сам по себе,
независимо от уровня.

## 4. Сигнатура коллапса и валидация детектора (измерено)

Все четыре коллапса идентичны по форме и совпадают с вариантом №2 из
[06](06-gateway-recon-keyless-oracles.md) §3:

```
content:            null (0 символов)
reasoning_content:  "The" + "!"×32   (или "The user" + "!"×32)  — 35–40 символов
finish_reason:      stop
HTTP:               200
```

Детектор `extensions/degenerate.ts` поймал **все четыре** как
`verdict = collapse, where = thinking`: сработало правило доли одного символа
(`!` ≈ 32/35 = 0.91 > 0.75 при длине ≥ 16). Признак сжимаемости здесь не нужен —
текст короче 300 байт, — что подтверждает правильность двухпризнаковой схемы из
06 §4. Важное уточнение к 06 §4: это **не** `empty-stop`, хотя `content` пуст, —
`reasoning_content` непуст и вырожден, поэтому классификатор правомерно выбирает
более точный `collapse` (проверка reasoning идёт раньше проверки «пусто+stop»).

Это первое воспроизведение коллапса **напрямую у NIM** (в 06 §3 он наблюдался
через сторонний шлюз) и первая боевая проверка детектора на живом выводе.

## 5. Выводы для кода

**Маппинг (измерено, внесено в `overrides/models.json`):**

```jsonc
"moonshotai/kimi-k3": {
  "reasoning": true,
  "compat": { "supportsReasoningEffort": true },
  "thinkingLevelMap": {
    "off": "none", "minimal": "minimal", "low": "low",
    "medium": "medium", "high": "high", "xhigh": "xhigh", "max": "max"
  }
}
```

`supportsReasoningEffort: true` активирует нативную ветку pi; карта задаёт
валидные варианты NIM; `off → "none"` — единственный валидный токен выключения.
Уровни `minimal`/`medium`/`xhigh`/`max` не пробовались поведенчески по отдельности
(пробованы `none`/`low`/`high`/`absent`), но их **валидность** как вариантов
доказана перечнем в 400-ответе (§2), поэтому 400 им не грозит.

**Гипотеза 06 §3 «off→null спасёт от коллапса» — ОПРОВЕРГНУТА (измерено).**
Проба `absent` (= то, что дал бы `off: null`) тоже коллапсирует (1 из 2) и тоже
медленная/таймаутная. Коллапс kimi-k3 **не зависит от значения
`reasoning_effort`** — это нестабильность самой модели на NIM, а не артефакт
маппинга. Поэтому `null` не лучше `none`, а хуже: `none` хотя бы валиден и
управляем селектором, тогда как `absent`/`null` — неограниченное рассуждение.

**Что НЕ меняется:** `transform.ts` (kimi остаётся на нативном пути, хук не
нужен — NIM принимает стандартный top-level `reasoning_effort`, измерено 200 на
`none`/`low`/`high`). Ротация/прокси/повторы не при чём: коллапс распределён по
запросам одного ключа и лечится повтором, а не сменой ключа.

**Роль детектора.** kimi-k3 коллапсирует ~в половине завершённых прогонов на
тривиальном промпте. Транспорт бессилен (контент уже стримится), прозрачный
повтор продублировал бы вывод. Поэтому правильный уровень — ровно тот, что уже
реализован в `degenerate.ts` + `message_end`: наблюдение, счётчик в
`/nvidia-plus status`, одно дросселированное предупреждение с подсказкой
«повторите запрос; max_tokens не поможет». Проба показала, что детектор для этой
модели не гипотетический, а рабочий.

## 6. Отрицательные результаты и границы

1. **Латентность ~2–4 мин на ответ** — свойство NIM kimi-k3, а не маппинга;
   фикс её не убирает. Короткий таймаут (<150 с) даёт ложные «зависания» на
   честных медленных ответах: приёмочная `absent`-проба таймаутнула на 150 с, а
   в фокусной (260 с) тот же `absent` дважды завершился за 136–170 с.
2. **Выборка мала** (9 фокусных прогонов). Доли коллапса (none 2/4, low 1/3,
   absent 1/2) — порядок величины, а не точная оценка; согласуются с 06 §3
   (none 31%, low 25% через шлюз). Для точной статистики нужны десятки прогонов.
3. **Промпт один** (тривиальный `Reply with OK`). Коллапс reasoning-канала на
   тривиальном промпте — воспроизводим; на содержательных промптах доля может
   отличаться. Не измерялось.
4. **`minimal`/`medium`/`xhigh`/`max` поведенчески не пробовались** — только их
   валидность как вариантов (§2). Доля коллапса на этих уровнях — гипотеза.
5. Пробы тратили реальную квоту ключа pi; серия ограничена 14 запросами
   (5 приёмочных + 9 фокусных), дальше не расширялась намеренно.
