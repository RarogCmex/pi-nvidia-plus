# 06 — Сторонний шлюз NIM как источник свидетельств и keyless-оракулы

Дата проб: **2026-10-05**. Метод: (а) read-only разведка стороннего открытого
прокси поверх NIM; (б) **keyless**-пробы `integrate.api.nvidia.com` — `GET /v1/models`
и `POST /v1/chat/completions` **без заголовка `authorization`**. Ни один запрос
не потратил квоту ключа: все пробы либо не требуют авторизации, либо отвергаются
до неё. Собственный ключ в этой сессии не использовался (его нет в окружении).

Файл отвечает на два вопроса: **что можно узнать о NIM без ключа** и **какой класс
отказов моделей мы пока не ловим**. Разбор стороннего шлюза здесь — не цель, а
источник свидетельств: он дал доступ к живым ответам NIM без нашего ключа.

Легенда достоверности, как в остальных файлах `research/`:

- **измерено** — прямой ответ `integrate.api.nvidia.com` в этой сессии;
- **измерено через шлюз** — ответ NIM, прошедший через сторонний прокси; модель
  ответа и `usage` принадлежат NIM, но транспорт чужой;
- **гипотеза** — экстраполяция, требующая живой пробы с ключом до попадания в код.

## 1. Keyless-оракул разрешения модели (главная находка)

`POST /v1/chat/completions` **без `authorization`** — это не просто 401. NIM
резолвит модель **до** проверки авторизации, поэтому ответ различает три исхода.
Все три подтверждены точными телами и `content-type`:

| Ответ | `content-type` | Тело | Значение |
|---|---|---|---|
| `404` | `text/plain; charset=utf-8` | `404 page not found` (19 байт) | chat-роута у модели **нет вообще** — нечат-модель |
| `401` | (не указан) | `Header of type \`authorization\` was missing` | chat-роут **есть**; живость модели не определяется |
| `410` | `application/problem+json` | `{"type":"about:blank","title":"Gone","status":410,"detail":"The model '…' has reached its end of life on <дата>T…Z and is no longer available."}` | модель снята с публикации, **с точной датой EOL** |

### Валидация

Прогон по всем **80** моделям живого каталога (`max_tokens:1`, пауза 150 мс):

```
401 → 71 модель      chat-роут есть
404 →  9 моделей     chat-роута нет
410 →  0 моделей     (EOL-модели из /v1/models исчезают, поэтому 410 возможен
                      только на id ВНЕ каталога)
```

Все девять `404` — действительно нечат: семь эмбеддингов/ретрайверов
(`nvidia/embed-qa-4`, `nvidia/nemotron-3-embed-1b`, `nvidia/nv-embedqa-mistral-7b-v2`,
`nvidia/llama-3.2-nv-embedqa-1b-v1`, `nvidia/llama-3.2-nemoretriever-1b-vlm-embed-v1`,
`nvidia/llama-nemotron-embed-vl-1b-v2`, `snowflake/arctic-embed-l`), клип
(`nvidia/nvclip`) и completion-модель (`bigcode/starcoder2-15b`).

`410` проверен на двух id вне каталога — оба дали точную дату EOL:
`meta/llama-3.3-70b-instruct` → EOL `2026-08-26T09:00:00Z`,
`meta/llama-3.1-70b-instruct` → EOL `2026-08-26T09:00:00Z`. Обе уже стоят в
`DEAD_MODELS` как «410 EOL» — совпадает.

### Что оракул НЕ умеет (границы)

1. **Не определяет живость чат-модели.** 401 означает «роут есть», а не «модель
   отвечает». Класс «404 in every probe» из аудита 02 оракул подтвердить не может:
   все 21 таких моделей дают keyless **401**, потому что авторизация идёт раньше
   вызова функции. Разные слои: keyless `404 page not found` (text/plain, HTTP-роутер)
   ≠ авторизованный `404 Function … Not found` (JSON, слой вызова функции NVCF).
2. **Не видит EOL модели, ещё присутствующей в каталоге.** 410 отдаётся только на
   id, уже снятый с публикации.
3. **Равенство keyless- и keyed-каталога не доказано.** Аудит 02 (2026-08-26) видел
   **83** модели с ключом; keyless-запрос 2026-10-05 дал **80**. Разница объяснима
   шестинедельным оттоком моделей, но строго доказать «keyless-листинг == keyed-листинг»
   без ключа нельзя. До проверки — считать гипотезой.

### Куда это ложится в расширении

- `discovery.ts` — `isChatModel()` сегодня чисто лексический. Оракул даёт
  ground truth без ключа и без квоты; им можно **сверять** эвристику (см. §2) или
  подменять её там, где сеть доступна.
- `DEAD_MODELS` — `410` + `application/problem+json` даёт **точную дату EOL**
  без ключа. Сегодня часть записей датирована только датой нашей пробы
  («probed 2026-09-18»), а не датой снятия с публикации.
- `key-check.ts` — `classifyKeyProbeStatus` трактует 401 как `dead` (ключ). Это
  верно для своей задачи, но рядом стоит помнить: 401 на **пустом** ключе означает
  «роут жив», а не «модель мертва».

## 2. Найден ложно-положительный в `NON_CHAT_PATTERNS`

Сверка эвристики `isChatModel()` с оракулом по всем 80 моделям каталога:

| Показатель | Значение |
|---|---|
| Оракул: chat-роута нет | 9 |
| Эвристика: считает нечатом | 21 |
| Согласие «нечат» | **8 из 9** |
| Ложно-положительные (эвристика пропускает в чат, роута нет) | **1** |
| Эвристика строже оракула (отсеивает, роут есть) | 13 |

**Единственный ложно-положительный — `bigcode/starcoder2-15b`.** Ни один из 15
паттернов его не ловит, поэтому в `classifyDiscovery` он попадает в `newChat` и
может быть предложен пользователю как новая чат-модель, хотя `POST /v1/chat/completions`
на него даёт `404 page not found` — chat-роута нет в принципе. В `test/discovery.test.ts`
список `nonChat` содержит ровно остальные восемь моделей из этой девятки; девятая пропущена.

**Фикс должен быть узким.** Все остальные кодовые модели каталога chat-роут имеют
(keyless `401`): `meta/codellama-70b`, `google/codegemma-7b`, `google/codegemma-1.1-7b`,
`mistralai/codestral-22b-instruct-v0.1`, `ibm/granite-8b-code-instruct`,
`ibm/granite-34b-code-instruct`, `deepseek-ai/deepseek-coder-6.7b-instruct`.
Значит паттерн «всё кодовое» сломал бы семь живых моделей. `starcoder` — семейство
FIM/completion, у него нет чат-варианта, поэтому бить надо по имени семейства.

**13 случаев «эвристика строже оракула» — не баг.** `guard`/`reward`/`translate`/
`parse`/`detector`/`calibration`/`deplot` формально имеют chat-роут, но как
чат-ассистенты бесполезны; комментарий в `discovery.ts` прямо говорит, что список
консервативный по смыслу, а не по наличию роута. Оракул и эвристика отвечают на
разные вопросы («есть ли роут» против «полезна ли как чат»), и держать нужно оба.

## 3. Непокрытый класс отказа: деградация вывода при HTTP 200

`stream-errors.ts` ловит **обрыв** потока: нет финального чанка с `finish_reason`,
pi-ai бросает `Stream ended without finish_reason`. Замеренный ниже отказ — другой:
поток **не** обрывается, `finish_reason` присутствует и равен `stop`, `usage`
корректен, HTTP 200. Портится само содержимое. Для транспорта это успешный ответ.

Замеры **через шлюз** (апстрим — тот же NIM, `reasoning_effort` шлюз передаёт
дословно, см. §5):

| Модель | Режим | Брак | Вид брака |
|---|---|---|---|
| `moonshotai/kimi-k3` | `reasoning_effort: "none"` | **11 из 36 = 31%** | `content` = `"The!!!!!!!!…"` |
| `moonshotai/kimi-k3` | `reasoning_effort: "low"` | **2 из 8 = 25%** | `content: null`, `reasoning_content` = `"User!!!!…"`, `finish_reason: stop` |
| `nvidia/nemotron-3-super-120b-a12b` | `thinking` выключен | 1 случай | **4000 токенов** `42424242…`, `finish_reason: length` |
| `nvidia/nemotron-3-ultra-550b-a55b` | `thinking` выключен | **0 из 10** | — |
| `moonshotai/kimi-k3` | `tool_choice: "required"` | всегда | `"<|close|>!!!!!!!!"` — утечка special-токена |
| `moonshotai/kimi-k3` | роль `developer` | всегда | `"!!!!!!!!"` |

Корреляции с ключом нет: коллапсы распределены по четырём разным слотам пула, то
есть это не «один плохой ключ». Второй прогон после первого не повторяет брак
(10 из 10 чисто при четырёх попытках) — отказ интермиттирующий, лечится повтором.

Отдельно опасен **второй** вариант: `content: null` при `finish_reason: stop`
выглядит как «кончился бюджет токенов», но увеличение `max_tokens` не помогает —
бюджет не исчерпан. Диагноз «пусто ⇒ поднять `max_tokens`» здесь неверен.

### Статус для нашего кода

**Гипотеза, не свидетельство.** Все измерения сделаны через сторонний шлюз с
`reasoning_effort: "none"`. Наши оверрайды маппят `off` в `"off"`
(`overrides/models.json`: `moonshotai/kimi-k3.thinkingLevelMap.off = "off"`), а не
в `"none"`. Принимают ли NIM-напрямую `"off"` для kimi и деградирует ли он так же —
**не проверено**, нужен ключ. До живой пробы ничего в `transform.ts` и в оверрайдах
менять нельзя (правило «каталог — только по свидетельствам»).

Что можно сделать без ключа: сам **детектор** — чистая функция над текстом, она
не зависит от транспорта и проверяется офлайн. См. §4.

Проба, которая закроет гипотезу (когда появится ключ): `stream: false`,
`max_tokens: 4000`, одна и та же короткая инструкция, 20 прогонов на
`moonshotai/kimi-k3` при `off`→`"off"` и 20 при `low`→`"low"`; считать долю
ответов, где детектор §4 срабатывает. Если на `"off"` доля заметно ненулевая —
маппинг `off` для kimi надо пересматривать (например, в `null`, как уже сделано
для `openai/gpt-oss-20b`).

## 4. Детектор repetition-collapse: рабочий алгоритм и почему наивный не работает

Проверен на живых корпусах и на реальных бракованных ответах.

**Наивный вариант «доля самого частого n-грамма» НЕ РАБОТАЕТ.** На реальном
коллапсе `42` × 2000 (4000 символов) граммы делятся поровну между `42` и `24`,
поэтому доля топ-грамма ровно **0.50** — при n = 1, 2, 3, 5 и 8 одинаково. Любой
порог выше 0.50 такой коллапс пропускает. Это измерено, а не предположено: первая
версия детектора именно так и промахнулась на настоящем ответе модели.

**Рабочий набор из трёх признаков** (по убыванию надёжности):

1. **Сжимаемость.** `len(zlib.compress(t, 9)) / len(t) < 0.08` при `len(t) >= 300`,
   где `t` — ответ с вырезанными пробелами. Циклический текст ужимается почти в ноль.
2. **Доля одного символа.** `> 0.75` при `len(t) >= 16`. Ловит короткие
   `"The!!!!…"` на 30 символах, куда признак 1 не дотягивается.
3. **Утечка special-токена.** `/<\|[a-z_]{2,20}\|>/` в исходном тексте — признак
   сломанного chat-template (`<|close|>`).

**Калибровка на живых ответах** (порог 0.08 выбран с запасом в обе стороны):

| Корпус | Длина | zlib ratio | Исход |
|---|---|---|---|
| связная русская проза ~250 слов | 1566 | **0.413** | пропущен ✅ |
| сгенерированный JSON, 20 объектов | 1804 | **0.160** | пропущен ✅ |
| коллапс `42` × 2000 (реальный ответ nemotron) | 4000 | **0.007** | пойман ✅ |
| коллапс `!` × 3000 (реальный ответ kimi) | 3000 | **0.009** | пойман ✅ |
| период-3 `abc` × 1500 | 4500 | **0.007** | пойман ✅ |

Ближайший легитимный корпус (JSON, 0.160) выше порога вдвое; ближайший брак
(0.009) ниже почти в девять раз. Запас позволяет не тюнинговать порог под каждую модель.

**Различение двух пустых ответов** (важно для правильного сообщения пользователю):

| `content` | `finish_reason` | Диагноз | Действие |
|---|---|---|---|
| пустой/`null` | `length` | бюджет съеден рассуждением | поднять `max_tokens` |
| пустой/`null` | `stop` | дегенерация reasoning-канала | **повторить запрос**, не трогать `max_tokens` |

Юнит-набор из 9 кейсов (коллапс в content, коллапс в reasoning, период-2,
period-3, утечка токена, проза, JSON, короткий ответ, честная нехватка бюджета)
прошёл 9/9. Реализация-эталон лежит в `~/pi-evals/xrouter-9/nva` (bash+python,
не для поставки — только как проверяемый образец алгоритма).

### Куда это легло бы у нас

Прямая аналогия со `stream-errors.ts`: чистый модуль-классификатор без pi и сети
(`degenerate.ts`), юнит-тесты офлайн, наблюдение на `message_end`, метрика в
`metrics.ts`, строка в `i18n.ts` на обоих языках. Транспортный уровень бессилен
так же, как при обрыве потока: контент уже стримится в pi, прозрачный повтор
продублировал бы вывод. Поэтому — наблюдение и уведомление, не подмена ответа.

## 5. Сторонний шлюз: что стоит перенять в архитектуре

Разобранный объект: `unified-nvidia-api.vercel.app` — публичный исходник
`github.com/AstwareDev/unified-nvidia-api` (Next.js 16.3.3, Vercel, последний
push 2026-09-01, лицензия отсутствует). Задеплоен публичный HEAD: живой `/docs`
рендерится из `AI_API_GUIDE.md` (`force-static` + `fs.readFile`), уникальные строки
совпадают. **Роутером не является** — это key-rotation прокси со статическим
whitelist'ом из 8 моделей в один апстрим: в `models.ts` нет ни одного поля
маршрутизации (`endpoint|upstream|baseUrl|url|path` — ноль совпадений), путь
`/chat/completions` константный, неизвестная модель отсекается до апстрима
(404 в конверте шлюза против RFC7807-конверта NIM). Авторизации нет; пул — 6
чужих ключей `nvapi-*`; значения ключей наружу не отдаются никогда.

Приёмы, которые у них сделаны удачно и совпадают с нашими задачами:

1. **Lease всего пула в повёрнутом порядке на каждый запрос**, а не одного ключа.
   Курсор сдвигается один раз на запрос, дальше запрос получает весь пул начиная
   со своей позиции. Первый ключ, вернувший 429/5xx, не роняет запрос — он уходит
   на следующий. Это тот же принцип, что в нашем `rotation.ts`, полезно как
   независимое подтверждение выбора.
2. **Benched-ключи сдвигаются в конец очереди, а не исключаются.** Кулдаун 30 с на
   429 и 10 с на 5xx/сеть; если в кулдауне весь пул, запрос всё равно уходит —
   на наименее остывший ключ. Искусственного отказа «все ключи заняты» не
   возникает. Наша quarantine-логика решает ту же задачу; их вариант — простое
   эталонное сравнение.
3. **Неретрайбельные 4xx не жгут остальной пул.** Плохая модель или битое тело
   провалятся одинаково на любом ключе, поэтому ответ возвращается сразу.
4. **Диагностические заголовки без секретов**: `X-Nvidia-Key-Id` (синтетический
   слот `key_3`, никогда не материал ключа), `X-Nvidia-Attempts`,
   `X-Nvidia-Max-Tokens`, `X-Thinking`, `X-Reasoning-Effort` /
   `X-Reasoning-Effort-Upstream`. Последняя пара интересна для нашей диагностики
   thinking: видно, какой уровень запросил клиент и какой реально ушёл в NIM.
   У нас эквивалент есть в `debug(...)`, но не в виде, доступном пользователю.
5. **`GET /v1/keys` — маскированная телеметрия пула** (счётчики запросов, успехов,
   429, ошибок, остаток кулдауна). Состояние живёт в памяти инстанса, поэтому при
   нескольких инстансах телеметрия не глобальная: замеры показали раскладку
   `key_1×5, key_2×2, key_3×1` на восьми параллельных запросах и `available_keys`,
   плавающее 6 → 4. Для нас урок обратный: **сессионные счётчики `metrics.ts`
   правильнее их подхода**, потому что у pi один процесс на сессию.

Что у них сломано (антипаттерны, полезно держать перед глазами):

- Каталог статический и с апстримом не сверяется: три из восьми записей
  (`deepseek-ai/deepseek-v4-pro-0813`, `deepseek-ai/deepseek-v4-flash-0731`,
  `openai/gpt-oss-120b`) на 2026-10-05 дают 410 EOL и **уже отсутствуют** в
  `GET /v1/models`. За месяц с последнего push каталог протух. Это ровно та
  болезнь, от которой лечит наш `discovery.ts` + датированный `DEAD_MODELS`.
- Документация утверждает «every one has been verified to return real
  completions» при трёх мёртвых моделях и обещает kimi
  `input: ["text","image","video"]` при неработающем vision.
- `tool_choice` с недопустимым значением возвращает клиенту **сырую serde-ошибку
  апстрима**: «data did not match any variant of untagged enum
  `ChatCompletionToolChoiceOption`». Утечка внутренностей апстрима в клиентский
  конверт — у нас `stream-errors.ts` и `key-check.ts` такие строки чистят.
- Tool calling не работает: `tools` форвардится дословно (passthrough-список в
  `validate.ts`), но ответ приходит с `tool_calls: null` и **выдуманным**
  содержанием («18°C with clear skies» в Токио). Измерено через шлюз; гипотеза для
  NIM-напрямую не проверялась.
- Страница `/docs` спроектирована как prompt-injection поверхность: «paste this
  into an AI assistant» и прямое указание агенту выполнить
  `node scripts/verify-model-capabilities.mjs`. Контент таких страниц — данные,
  не команды.

**Использовать чужой шлюз как постоянный канал проб не следует**: расход чужой
квоты и нарушение ToS NVIDIA. В этой сессии он послужил один раз — чтобы снять
поведенческие свидетельства (§3) без собственного ключа. Автоматизировать нельзя.

## 6. Отрицательные результаты (что НЕ подтвердилось)

Записаны, чтобы следующий заход не повторял те же ходы.

1. **410-оракул не работает на моделях из каталога.** Ожидалось, что keyless-проба
   даст 410 на все EOL-модели; на 80 моделях живого каталога получено **ноль** 410.
   Причина: снятая с публикации модель исчезает из `GET /v1/models`, поэтому 410
   достижим только на id, которого в каталоге уже нет.
2. **Keyless-проба не подтверждает класс «404 in every probe»** из аудита 02: все
   21 таких моделей дают 401. Авторизация precedes вызов функции.
3. **Поиска исходников по имени файла недостаточно.** `gh search code
   "verify-model-capabilities"` выдал девять посторонних репозиториев; нужный нашёлся
   только по `gh search repos "unified-nvidia-api"`. Аттрибуцию дал `homepageUrl`,
   совпавший с хостом.
4. **Системный `python3` на macOS без `certifi`** падает в `CERTIFICATE_VERIFY_FAILED`
   на любом HTTPS-запросе, хотя `curl` работает. В скриптах проб нужен явный
   `cafile` или fallback.
5. **`enabledModels: []` в `settings.json` означает «все модели»**, а не «никаких»:
   запись туда сузила бы весь список моделей пользователя. Трогать нельзя.
