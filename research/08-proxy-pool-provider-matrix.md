# 08 — Матрица «выход × провайдер»: что пул прокси годится обслуживать

**Дата:** 2026-10-10 (вечер) · **Метод:** keyless-пробы каталогов (`GET /v1/models`
и аналоги) через агент каждого выхода пула, 2 раунда на пару «выход × цель»,
таймаут 20 с, undici из бандла pi. Инструмент — `scripts/proxy-pool-audit.mjs
audit --providers …` (после коммита 6da0d1e). Ни одного ключа, ни одного токена
генерации: все 29×16×2 = 928 проб бесплатны.

**Вопрос:** пул `nvidia-proxies.json` однороден ли по качеству — годится ли
данный выход только для NIM или вообще для любого OpenAI-совместимого API?
Практическая постановка: если какой-то выход невидим для части провайдеров,
это надо знать ДО того, как через него пойдёт рабочий трафик.

## Результаты

29 выходов × 16 целей (NVIDIA NIM, OpenAI, Anthropic, OpenRouter, Google
Generative Language, Groq, DeepInfra, Together, Mistral, DeepSeek, xAI,
Cerebras, SambaNova, Cohere, Fireworks, Hugging Face Router).

**NIM (решающая цель):** 29/29 выходов — 2/2 проб, задержки 95–2793 мс
(максимум — первый хит у «холодных» шлюзов; устойчивая латентность 90–600 мс).
Вывода для пула: пул однороден, выбрасывать нечего.

**Остальные 15 целей (справка):** 27 из 29 выходов прошли ВСЕ 16 целей.
Два исключения:

| Выход | Проблемные цели | Форма отказа |
|---|---|---|
| `p.webshare.io` | openai, google, groq, xai, cerebras, fireworks, huggingface (0/2), openrouter (в раннем прогоне 0/2, здесь 2/2 — плавает) | `hang`: первый раунд T/O, второй местами проходит (948–1316 мс) — селективная фильтрация, а не мёртвый маршрут |
| `194.50.189.21:29842` | cerebras: 1/2 (T/O, затем 682 мс) | единичный срыв на одной цели |

## Выводы

1. **Провайдер-селективность выходов реальна и измерима.** `p.webshare.io`
   (ротационный шлюз webshare) обслуживает nvidia, anthropic, deepinfra,
   together, mistral, deepseek, sambanova, cohere — и виснет на openai, google,
   groq, xai, cerebras, fireworks, huggingface. Паттерн T/O-затем-ответ больше
   похож на селективную фильтрацию по IP/ASN со стороны этих провайдеров (или
   их CDN), чем на неработающий маршрут. Для пула NIM это не дефект; для
   «пустить через этот выход что-то ещё» — стоп-сигнал, который виден только
   матрицей.
2. **Качество выхода для NIM не предсказывает качество для других целей.**
   Худший по матрице выход — не худший для NIM (у webshare-выхода латентность
   к NIM 210–1139 мс — одна из лучших в пуле). Поэтому матрица — справка
   (`notes`), а гейт приёмки в пул решает только цель из `--require` (NIM):
   иначе гео-блок одного провайдера выбрасывал бы рабочий выход.
3. **2 раунда — разведка, не приёмка.** Вердикт `hang` при «T/O затем ответ»
   при 2 раундах может быть прогревом. Приёмка новых выходов идёт 3+ раундами
   (`--rounds`); матрица же отвечает на вопрос «кому служит», а не «стабилен ли».

## Методологические оговорки

- Пробы шли последовательно по целям (16 проходов планировщика по 29 выходам,
  параллельность 4 внутри прохода) — проведено одним прогоном ~20 минут.
- Три цели отвечают на keyless-запрос не-JSON телом (together 401 text/plain,
  deepseek 401 без content-type, cohere 403 text/html) — для них expectation
  `any` + зажатие статусов, см. комментарий `PROBE_TARGETS` в скрипте.
- Рабочие отчёты прогона: gitignored `test-results/matrix-full.json`
  (latencies и все серии), в репозиторий не входят.
